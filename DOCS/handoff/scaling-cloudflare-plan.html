Scaling test, cost per school & the move to Cloudflare

One piece of work with three results: how many schools the platform can carry before it slows down, what each school costs us per month, and whether we move hosting from Vercel to Cloudflare. We get all three by running the same tests on the same synthetic schools.

01 · Goal

What we'll know at the end

The ceilingHow many schools at peak (9 AM attendance, results day) before pages pass 1.5 s or errors pass 1%, and what breaks first.
Cost per school₹ per school per month and per active user, at 10, 50, 200 and 500 schools, on Vercel Pro and on Cloudflare.

02 · Ground rules

Testing rules we have to follow

We can't load-test on Vercel.Vercel only allows load testing on Enterprise plans; on other plans the testing IPs get blocked and it can breach fair use. So Vercel's numbers come from production's own usage dashboard (real traffic), not from a load test.
  • Never production. No load against welearnyoulearn.com or the production database. Tests use a separate staging database with synthetic schools only, no copies of real student data.
  • Cloudflare: we may test infrastructure we own. We test the preview Worker on our own account and open a support ticket with the test window first, so DDoS protection doesn't block the test.
  • The local dev database (.env) is not used for load either; it stays for development.
  • Reading production's traffic numbers (logins, sessions per school) is read-only and done by whoever holds production access (Q4).

04 · Realistic load

What one school looks like

We size each synthetic school from production's real traffic, not guesses. The platform already records logins, time spent and features opened per school and role (usage_daily_rollup, feature_usage_events). These read-only queries give the profile:

-- Per school, per role, per weekday (last 30 days): active people, logins, minutes
SELECT school_id, actor_role, EXTRACT(ISODOW FROM day) AS weekday,
       ROUND(AVG(unique_actors)) AS people, ROUND(AVG(login_count)) AS logins,
       ROUND(AVG(total_duration_seconds) / 60) AS minutes
FROM usage_daily_rollup WHERE day >= CURRENT_DATE - 30
GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;

-- Busiest hours (IST) across all schools
SELECT EXTRACT(HOUR FROM started_at AT TIME ZONE 'Asia/Kolkata') AS hour, COUNT(*) AS sessions
FROM usage_sessions WHERE started_at >= NOW() - INTERVAL '30 days' GROUP BY 1 ORDER BY 1;

-- What people open most, per portal (drives the mix of pages in the scripts)
SELECT portal, nav_key, COUNT(*) FROM feature_usage_events
WHERE created_at >= NOW() - INTERVAL '30 days' GROUP BY 1, 2 ORDER BY 3 DESC LIMIT 40;

Until those numbers arrive, the scripts start from this assumed school, then get corrected:

05 · Scenarios

Five tests, each at four sizes

ScenarioWho does whatWhy it matters
1 · Morning attendanceEvery teacher logs in and marks attendance for their class within 30 min (/api/attendance).The sharpest daily peak; many writes at once.
2 · Parents' eveningParents log in, open child summary, attendance and fees (/api/parent/*), 7–9 PM.The largest number of people; mostly reads.
3 · Fee dayAdmins collect payments and open the ledger and reports (/api/fees/*) while parents check dues.Heavy queries and money writes together.
4 · Results day60% of parents open marks within 2 hours of publishing.A burst well above normal; tests cold starts and caching.
5 · Heavy jobs500-student import, a full Excel export, the nightly backup, during scenario 2.Long-running work that can hit time and memory limits, especially on Workers (128 MB, CPU time).
  • Sizes: 1× (today's live school count), 5×, 20×, 50× schools, each ramped over 10 minutes and held for 20.
  • Stop a run early when p95 response time passes 2 s, errors pass 1%, or database CPU stays over 90%.
  • Each run starts from a freshly seeded database so results compare fairly.

What we expect to find (to confirm or rule out)

  • Database connections run out first. Each Vercel function holds one connection through Supabase's session pooler; a busy morning may use them all before CPU is a problem.
  • Cold starts are slow because every new instance runs ~115 migration statements (instrumentation.ts).
  • A few heavy screens (fee ledger, reports, exports) dominate database time.

08 · Hosting

Moving to Cloudflare

Known risk for our exact setup.Next.js 16.3 apps whose proxy.ts loads instrumentation.ts fail on Cloudflare's runtime. Step 1 below removes that dependency, and it's worth doing on any host.
  1. Migrations out of startup: run scripts/run-migrations.ts as a deploy step; instrumentation.ts stops touching the database. Faster cold starts everywhere.
  2. Adapter: add @opennextjs/cloudflare and wrangler.jsonc with nodejs_compat; build and deploy dev to a preview Worker.
  3. Database: connect through Hyperdrive to Supabase (pooled, close to the Worker); remove the Vercel-only pool sizing in lib/db.ts.
  4. Scheduled jobs: the 9 jobs in vercel.json become Cloudflare Cron Triggers calling the same /api/cron/* routes with CRON_SECRET. Long ones (backup) must fit the cron CPU limit or be split.
  5. Limits: bundle size (10 MB), memory (128 MB) and CPU time (raise to 5 min where needed) for exports, imports and backup.
  6. Settings and branches: secrets per environment; prod → production, qa/dev → previews.
  7. Full Playwright suite against the preview Worker, then the load tests (Target B).
  8. Cutover (after go): move DNS for welearnyoulearn.com and admin. to Cloudflare in a late-night window, watch for an hour, keep Vercel running 2 weeks for instant rollback.

If the trial fails: move production to Vercel Pro straight away (we can't charge schools on the free plan), and retry Cloudflare once the adapter issue is fixed.

10 · Decision

Cloudflare go / no-go checklist

  • All Playwright tests pass on the preview Worker.
  • Login, proxy.ts redirects and plan locks work in all 5 portals.
  • All 9 scheduled jobs run from Cron Triggers.
  • 500-student import, a full Excel export, fee year-end and the backup each finish within limits.
  • p95 response time on Cloudflare is no worse than Target A at the same load.
  • Cost per school on Cloudflare is lower than on Vercel Pro at 50 schools and above.
