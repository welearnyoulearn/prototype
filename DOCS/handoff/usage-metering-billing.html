Feature handoff · draft for review

Plans, usage, traffic & hosting

Four connected pieces for taking WLYL to paying schools. Plans get real prices the platform admin controls. Usage records every paid service each school uses (WhatsApp, email, AI, storage, and later services) and bills the extra. Traffic shows visitors, sessions and time spent, kept separate from usage. Hosting covers the move off Vercel's free plan.

Date: 8 Oct 2026Base: origin/dev @ a75dc5aIssues: #358 (to be widened), #359Status: waiting on open questions
This replaces the WhatsApp-only credits plan.WhatsApp becomes one service among several. The earlier decisions still hold: bill monthly after use, and keep sending up to a limit. They now apply per service, and the platform admin sets them.
01 · Summary

What we are building

Plans with real pricesEach plan gets a monthly and yearly price, set by the platform admin together with its features, staff limit and included usage. A single school can get a discount.
Traffic, separate from usageVisitors, sessions and time spent, for the portals and the public website. Shown on its own Traffic page and never mixed into bills.
Hosting that allows commercial useVercel's free plan doesn't allow commercial use. The plan: a short Cloudflare trial, with Vercel Pro as the fallback.
Track everything, per schoolOne shared function records each use of a paid service against the school, with the amount and when it happened.
Prices set by the platform adminFor each service and plan: how much is included each month, the price per extra unit, and a monthly limit. No code change is needed to change a price.
Charge later, by switchEvery service is tracked from day one. Charging is switched on per service, once prices are agreed.
Add a service in one stepA new service (SMS, push, a new AI model) is a new row in the service list plus one tracking call in code. No database change.
Visible to both sidesSchools see this month's usage and estimated charges. The platform admin sees every school, sets prices, closes months into bills, and compares what we charge with what the service costs us.

Not in this feature

  • Online payment of bills (Cashfree). Bills are marked paid by hand for now.
  • Prepaid credit packs or wallets.
  • The plan fee itself, which stays with yearly renewals unless question Q8 says otherwise.
  • New services that don't exist yet, such as SMS. The design makes them easy to add later.

03 · Plans

Plans & prices

Today a plan decides which features a school gets and how many staff accounts it can have, but nothing sets what the school pays. This makes a plan one complete package that the platform admin edits in one place:

PriceMonthly and yearly price in ₹, GST shown separately. The yearly price can be discounted.
FeaturesThe existing per-plan feature switches, unchanged.
Staff accountsThe existing staff limit, unchanged.
Included usageHow many WhatsApp messages, AI tokens and so on are included each month, from the usage prices in this document.
VisibilityShown on the website or not, display order, and retired. A retired plan keeps its current schools but can't be given to new ones.

How a school's price works

  • When the platform admin gives a school a plan or renews it, the screen shows the plan's list price, the billing period (monthly or yearly), and an optional discount or custom price with a reason.
  • The agreed price is saved on that school's plan term. Later changes to the plan's price don't affect the school until its next renewal (Q16).
  • Starting or renewing a term creates a plan bill: once for a yearly term, or one line on each monthly bill for a monthly term (Q8).
  • Upgrades mid-term are charged for the remaining days, worked out from the agreed price (Q18). Downgrades take effect at renewal.
  • Every price, discount and plan change is written to platform_audit_log, as plan changes are today.

07 · For developers

Recording usage

New file lib/usage.ts. These are the only two functions the rest of the app calls. Each paid service plugs in at the shared helper it already goes through, never at individual screens.

// Before a costly action. Reads this month's total from usage_daily and the school's price (override → plan).
checkAllowance(schoolId, meterKey, quantity = 1)
  → { allowed: boolean, reason?: 'limit_reached' | 'not_in_plan', used, included, cap }

// After the provider accepted it. Never throws; a failure is logged to error_events.
recordUsage({ schoolId, meterKey, quantity, source, actor?, ref?: { type, id }, idempotencyKey?, meta? })
  → INSERT usage_ledger … ON CONFLICT (idempotency_key) DO NOTHING
  → UPSERT usage_daily  quantity = quantity + $n   (only if the insert happened)
  → threshold check → alert email once (usage_alerts_sent)

Where each call goes

  • WhatsApp: sendWhatsappMessage(), check before sending, record when Meta returns a message id. Idempotency key wa:<provider id>.
  • Email: sendMail(to, subject, html, { schoolId, source }). The new options argument is optional, so the 25 existing callers keep working, and emails without a school count as the platform's own use.
  • AI: callAI() records ai.request = 1 and ai.tokens from the response's usage.total_tokens. It's checked before calling, so a school at its limit gets a clear message instead of an AI answer.
  • Storage: the upload-confirm routes record the file size in MB. A nightly job adds up stored size per school for storage.gb_month.
  • API requests: proxy.ts runs where it can't reach the database, so it keeps a count in memory and sends one total per school every minute through the existing internal ingest route, instead of one row per request.
  • Active users: no new tracking. A nightly job counts each school's distinct users this month from usage_sessions.
08 · Money

Usage prices & charges

For each school, charged service and month:

price      = school override ?? plan price      (locked into the month when it starts)
used       = sum of usage_daily for the month
extra      = max(0, used − included)
units      = extra ÷ unit_size                  (e.g. 450,000 extra tokens ÷ 1,000 = 450)
line total = round(units × unit_price, 2)        (see Q5 for rounding up to whole units)
bill total = sum of line totals  (+ GST, see Q9)
Worked example example pricesA Standard school in October: 1,240 WhatsApp messages (1,000 included, ₹0.20 each after) → 240 × ₹0.20 = ₹48.00. AI: 1.45M tokens (1M included, ₹0.05 per 1,000 after) → 450 × ₹0.05 = ₹22.50. Emails: 3,400, tracked only, so no line. Bill: ₹70.50 before GST.
  • Prices are locked when a month starts, so an edit only affects the next month and no school's month is re-priced mid-way (Q6).
  • A service's "charged" switch only affects months that start after it's turned on. Earlier usage stays recorded, but nobody is charged for it retroactively.
  • Every price change is recorded in platform_audit_log with who changed it and the old and new values.

12 · Behaviour

Limits & alerts

  • Each charged service has a monthly limit per plan, which the platform admin can change for a single school. At the limit the service does what the price says: block (stop and tell the user why), allow (keep going and charge), or notify (keep going and alert the platform admin).
  • School admins get one email per service at 80% and at 100% of what's included each month. The platform admin gets a daily digest of schools that are over their limit or using far more than usual.
  • Messages a school can't do without (password resets, login details) can be exempt from blocking so parents are never locked out (Q7).
  • Known gap: the limit is checked just before each use, so many uses at the same moment can go a few units past the limit. That's acceptable at school scale; we'll lock per school and service if it ever matters.
13 · Non-negotiables

Security & accuracy

  • School data stays separate: school endpoints take the school only from the session, never from the request. Every platform endpoint requires requirePlatformAdmin().
  • No double counting: every record has an idempotency key (the provider's message id, file key, or request id), so retries don't count twice.
  • Usage counts never break the action: if recording fails, the WhatsApp message or email still goes out and the failure is logged in Watchline. A daily check compares usage counts with the provider logs we already keep (for example whatsapp_messages) and flags any gap.
  • Money is auditable: prices, overrides, each automatic bill run and every payment recorded are all written to platform_audit_log. A closed bill never changes; corrections become a new adjustment line (Q12).
  • No personal data in usage records: they hold ids and counts only, never message text, email addresses or file names.
  • Validation: all inputs go through Zod. Prices and limits have to be zero or more, with sensible upper bounds.
14 · Deployment

Hosting: moving off Vercel's free plan

We can't charge schools on the free plan.Vercel's Hobby plan is for non-commercial use only. Any site that takes payment or is built for financial gain needs Pro or Enterprise. We must move before the first school pays.

Today

  • Next.js 16.3.6 (App Router, proxy.ts, instrumentation.ts) on Vercel Hobby, under two accounts. Production deploys from the prod branch; qa and dev are previews.
  • 9 scheduled jobs in vercel.json (backup, plan expiry, exam reminders, birthday sweep, usage digest…).
  • Supabase Postgres (ap-south-1) through the session pooler, with 1 connection per function on Vercel. Cloudflare R2 already holds backups and files. Resend for email, Cloudinary for some images.
  • instrumentation.ts runs all database migrations (~115 statements) on every cold start.

Cloudflare move, step by step

  1. Trial (2 days): add @opennextjs/cloudflare and wrangler.jsonc (nodejs_compat), deploy dev to a preview Worker on the dev database, then run the full Playwright suite against it.
  2. Move migrations out of startup: run scripts/run-migrations.ts (already exists) as a deploy step and make instrumentation.ts a no-op. This avoids the known OpenNext issue and stops every cold start from running ~115 statements. Worth doing even if we stay on Vercel.
  3. Database: connect pg through Hyperdrive to Supabase (pooled, close to the Worker). Remove the Vercel-only pool sizing in lib/db.ts. Check that long transactions (fee year-end, bulk imports) still finish.
  4. Scheduled jobs: move the 9 jobs in vercel.json to Cloudflare Cron Triggers. They call the same /api/cron/* routes with CRON_SECRET, at the same times (UTC).
  5. Limits check: Worker bundle size (exceljs and PDF code are heavy), CPU time for backup, exports and bulk imports (raise the CPU limit or split the work), and the in-memory caches in proxy.ts, which become per-instance.
  6. Settings and branches: secrets via wrangler secret per environment. GitHub builds: prod → production, qa and dev → preview URLs. Images: keep next/image unoptimized or use Cloudflare Images.
  7. Domains: move welearnyoulearn.com and admin.welearnyoulearn.com DNS to Cloudflare with a low TTL. The platform-admin subdomain rule in proxy.ts stays.
  8. Cutover: a late-night window with schools told in advance. Switch DNS, watch Watchline errors and logs for an hour, and keep Vercel running for 2 weeks for instant rollback (switch DNS back).

Trial pass checklist

  • All Playwright tests pass against the preview Worker.
  • Login, proxy.ts redirects and the plan lock work in all 5 portals.
  • Every cron route runs from a Cron Trigger.
  • Fee year-end, a 500-row student import and an Excel export each finish within limits.
  • p95 page response is no worse than on Vercel in the scaling test.
  • Monthly cost estimate from the scaling test is below the Vercel Pro estimate.
